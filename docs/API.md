## 0. Scope and requirement mapping

DFSha is a **block-based DFS, HDFS-style** (Option 1: client/server, with the server composed of NameNodes and several DataNodes inside a private network; clients reach it over the Internet).

| Project requirement | Where it is covered |
|---|---|
| **RF1** File system management (`ls`, `cd`, `mkdir`, `rmdir`, `rm`, …) | Section 4.3 · `cd` is client-side state validated with `stat` |
| **RF2** File transfer (`send()` / `receive()`) | Sections 5 and 6 · Library: `put_file`, `get_file` |
| **RF3** File access (`open`, `close`, `read`, `write`, `lock`) | Sections 4.4 (`lock`), 5.4, 10 (`open`/`close`/`read`/`seek`; `write` is block-level via `write_block` + `put`, because files are WORM) |
| **Professor's requirement:** _"APIs for basic read/write operations on files (blocks) from the client"_ | **Block level:** gRPC `WriteBlock` / `ReadBlock` (Section 6) + `read_block` / `write_block` (Section 10). **File level:** Sections 5 and 10. |
| Partitioning: files across nodes, each file across several nodes | Blocks of one file are placed on different DataNodes (Section 7, placement rules) |
| High availability / replication / consistency | Pipeline replication, quorum `commit`, re-replication (Sections 5, 6, 7); NameNode HA with lease and fencing (Section 9) |
| Security: encryption in transit and at rest, access control by user/group, API keys, node-to-node security | Section 2, 4.1, 4.2 |
| Transparency | The client never chooses nodes; the NameNode decides and the library hides it (Section 10) |

## 1. General conventions

| Topic | Decision |
|---|---|
| Protocol | **REST over HTTPS** for everything that involves the NameNode (Client ↔ NameNode, DataNode → NameNode), version prefix `/v1`. **gRPC (HTTP/2 + Protocol Buffers) over TLS** for the block channel (Client ↔ DataNode, DataNode ↔ DataNode). The DataNode does not expose an HTTP server. |
| Format | UTF-8 JSON on REST. Blocks travel over gRPC as **raw bytes in streamed chunks**; never JSON or base64 for blocks. |
| Dates | ISO-8601 in UTC (`2026-10-16T14:30:00Z`). |
| Sizes | Always in bytes (integers). |
| FS paths | Absolute, using `/`, inside the authenticated user's namespace (each user sees their own root `/`). No `.` or `..` segments; the NameNode rejects them with `400`. |
| Checksums | SHA-256 as lowercase hex, computed over the **plaintext block bytes exactly as sent by the client** (before encryption at rest, which is internal to each DataNode). |
| IDs | `file_id`: **UUID4 in canonical form** (`7b0c9e0e-5e0a-4a58-9a11-1f0c6a3d2b11`). `block_id`: opaque string generated by the NameNode (e.g. `blk_<file_id_short>_<index>`); other components must **not** parse it. |
| Block order | Each block has an `index` (0, 1, 2…). A file is rebuilt by concatenating blocks by `index`. |
| Transport security | HTTPS/TLS on REST and TLS on gRPC for all communication (plain HTTP and insecure gRPC channels are acceptable in local development only). |
| Unknown fields | Receivers **ignore** unknown JSON fields (REST) and unknown protobuf fields (gRPC). This lets us add fields without breaking anyone. |
| Tracing | Clients may send `X-Request-Id` (REST header) or `x-request-id` (gRPC metadata); every component echoes it in the response and includes it in its logs. If absent, the receiver generates one. |

### Public address vs internal address (important)

Every DataNode has two gRPC addresses, written as `host:port` (the target of a gRPC channel, no scheme):

- `internal_addr`: used by other DataNodes (e.g. `dn1:9000` inside Docker/VPC).
- `public_addr`: reachable **from the user's machine** (public IP or domain, e.g. `dn1.example.com:9000`).

Clients only ever receive `public_addr` values (called `addr` in the NameNode responses). In a single-network development setup both can be the same. TLS is always on; the certificate must be valid for the host name used in the address.

### Configurable parameters (environment variables, with defaults)

| Parameter | Default | Notes |
|---|---|---|
| `BLOCK_SIZE` | 64 MiB | Same default as HDFS in the course material. **Demo/test profile: 1 MiB** so small files produce many blocks. All sizes in this document are **binary** (MiB, GiB) |
| `BLOCK_CHUNK_SIZE` | 1 MiB | Size of each streamed chunk on the gRPC block channel (a DataNode rejects chunks above 2 MiB) |
| `REPLICATION_FACTOR` | 3 | Target replicas per block |
| `MIN_REPLICAS_COMMIT` | 2 | Write quorum: minimum confirmed replicas per block to allow `commit` |
| `MAX_FILE_SIZE_BYTES` | 10 GiB | In this version `put` allocates all blocks up front, so file size is bounded. Batched allocation is already designed (`ARCHITECTURE.md` Section 6.3) and will relax this to an optional quota; it changes Sections 5.1 and 5.5 and lands with its own version bump |
| `HEARTBEAT_INTERVAL_S` | 5 | DataNode → NameNode |
| `DEAD_NODE_TIMEOUT_S` | 30 | No heartbeat for this long ⇒ node is considered dead |
| `BLOCK_REPORT_INTERVAL_S` | 60 | DataNode → NameNode |
| `TOKEN_TTL_S` | 900 | Block token lifetime (renewable, see 5.5) |
| `UPLOAD_TTL_S` | 3600 | A `put` that is never committed is garbage-collected after this |
| `LS_DEFAULT_LIMIT` | 1000 | Default page size for `ls` |
| `LEASE_S` | 15 | NameNode leader lease duration (Section 9) |
| `FAILOVER_GRACE_S` | 30 | After a failover, the new leader waits this long before declaring any DataNode dead |
| `LOCK_DEFAULT_TTL_S` | 60 | Default lifetime of a file lock |
| `MFA_CHALLENGE_TTL_S` | 300 | Lifetime of the single-use login challenge returned when 2FA is enabled (Section 4.1.1) |

### Versioning policy

- Backward-compatible changes (new optional fields, new endpoints) stay in `/v1`.
- Breaking changes (renamed/removed fields, changed semantics) require `/v2` or an explicit team decision recorded in the change log.
- Every change to this file bumps the version at the top and adds a line to the change log.

## 2. Authentication and security

There are four mechanisms, one per type of communication:

| From → To | Mechanism | Header / metadata |
|---|---|---|
| User → NameNode | JWT (HS256 or RS256), issued by `/v1/auth/login`, or by `/v1/auth/login/2fa` when the user has **TOTP 2FA** enabled | `Authorization: Bearer <jwt>` |
| User/script → NameNode | **API key** (long-lived, revocable, same permissions as its owner, exempt from 2FA by design) | `Authorization: ApiKey <api_key>` |
| DataNode → NameNode | **Mutual TLS** (per-node certificate from the cluster CA) plus a cluster secret | client certificate + `X-Node-Key: <secret>` (+ `node_id` in the body) |
| Client / DataNode → DataNode (gRPC) | **Block token** issued by the NameNode | gRPC call metadata `x-block-token: <token>` |

### 2.1 Block token format

`token = base64url(payload) + "." + base64url(HMAC-SHA256(shared_secret, base64url(payload)))`

```jsonc
// payload
{
  "bid": "blk_7b0c9e0e_000000",   // block_id this token is valid for
  "op":  "w",                      // "r" = read, "w" = write
  "usr": "ana",                    // user it was issued to ("system" for replication commands)
  "exp": 1760625000                // UNIX seconds, expiration
}
```

The DataNode validates it **locally**, without calling the NameNode, in a gRPC server interceptor: signature, `exp`, that `bid` equals the `block_id` of the request, and that `op` matches the RPC (`WriteBlock` needs `w`; `ReadBlock` and `StatBlock` need `r`). A token for one block is useless for any other block.
The shared secret lives only in environment variables of NameNodes and DataNodes.

### 2.2 Other security rules

- Passwords are stored hashed (bcrypt or argon2), never in plain text. Login is the only endpoint that accepts credentials. API keys are stored hashed too and are shown **only once**, when created. TOTP secrets are stored encrypted and recovery codes hashed; both are shown only once, at enrolment (Section 4.1.1).
- The NameNode checks permissions (owner / ACL for user or group) **before** issuing any token, and re-checks on every FS operation.
- Each user can only see and modify their own namespace, plus paths shared with them (directly or through a group).
- A DataNode that cannot present a valid `X-Node-Key` cannot register, send heartbeats or report blocks.
- The NameNode keeps an **audit log** (timestamp, user, operation, path, result, `X-Request-Id`) of every authentication and FS operation.
- Roles: `user` (default) and `admin` (needed for Section 8). The first admin is bootstrapped from the `ADMIN_USER` / `ADMIN_PASSWORD` environment variables on first start.
- **TOTP 2FA** on interactive login and **mutual TLS** between nodes are required, not optional (Sections 2 and 4.1.1). Rate limiting applies to `login` and to 2FA code attempts.
- Optional hardening (stretch goals): per-node key rotation instead of one cluster secret, client-side encryption.

### 2.3 Encryption

| Where | Mechanism |
|---|---|
| **In transit** (all hops: client↔NameNode, client↔DataNode, DataNode↔DataNode, DataNode↔NameNode) | TLS on every hop: HTTPS for REST (client↔NameNode, DataNode↔NameNode) and TLS channel credentials for gRPC (client↔DataNode, DataNode↔DataNode). In the demo, a self-signed CA is acceptable if the clients trust it; certificates must be valid for the host names used in the `addr` values. |
| **At rest** (blocks on DataNode disks) | **AES-256-GCM, done by each DataNode.** Per-block key = `HKDF-SHA256(master_key, salt=block_id)`; random 96-bit nonce stored in the block file header; the GCM tag is verified on **every read** (tamper/corruption detection). |
| Key management | `DATANODE_MASTER_KEY` (32 bytes, base64) from environment/secret store, never committed to the repo. Each DataNode may have its own key: replication sends decrypted bytes over TLS and the target re-encrypts with its own key. |
| Optional: client-side encryption | `dfsha put --encrypt` encrypts blocks before upload (nodes just see opaque bytes). Out of scope for v1 sharing (no key exchange between users); documented as an extension. |

## 3. Error format

All **REST** error responses use the same body (the block channel uses gRPC status codes, see 3.1):

```json
{
  "error": {
    "code": "FILE_NOT_FOUND",
    "message": "/docs/report.pdf does not exist"
  }
}
```

| HTTP | `code` | When |
|---|---|---|
| 400 | `BAD_REQUEST` | Invalid parameters, JSON or path |
| 400 | `NOT_A_DIRECTORY` / `IS_A_DIRECTORY` | Operation applied to the wrong kind of path |
| 401 | `UNAUTHORIZED` | Missing, invalid or expired credentials/token |
| 403 | `FORBIDDEN` | No permission on the path or block |
| 404 | `FILE_NOT_FOUND` / `DIR_NOT_FOUND` / `BLOCK_NOT_FOUND` / `GROUP_NOT_FOUND` / `USER_NOT_FOUND` | Does not exist |
| 409 | `ALREADY_EXISTS` | The path (or user/group name) already exists |
| 409 | `UPLOAD_IN_PROGRESS` | Another uncommitted `put` holds this path |
| 409 | `DIR_NOT_EMPTY` | `rmdir` without `recursive` on a non-empty directory |
| 409 | `INSUFFICIENT_REPLICAS` | `commit` without the minimum confirmed replicas |
| 409 | `NODE_NOT_REGISTERED` | A heartbeat or block report from a `node_id` the leader does not know. The DataNode must `register` again and then send a full block report. Normal after a failover or a NameNode restart, not an error condition |
| 409 | `FILE_NOT_COMMITTED` | Attempt to read a file that has not been committed yet |
| 413 | `FILE_TOO_LARGE` | `size` exceeds `MAX_FILE_SIZE_BYTES` |
| 416 | `RANGE_NOT_SATISFIABLE` | Invalid `offset` / `length` on a block read |
| 422 | `CHECKSUM_MISMATCH` | The checksum does not match the received bytes |
| 423 | `LOCKED` | A conflicting lock held by another user (Section 4.4) |
| 429 | `RATE_LIMITED` | Too many requests; includes `Retry-After` (optional in v1) |
| 503 | `NOT_ENOUGH_DATANODES` | Not enough live DataNodes to place replicas |
| 503 | `NOT_LEADER` | This NameNode is not the leader; the body includes `leader_url` |

### 3.1 Errors on the block channel (gRPC)

The block channel has no HTTP status codes and no JSON body. Each error is a gRPC status code, plus the trailing metadata `x-dfsha-error-code` carrying the application `code` from the table above, so the same names appear in logs and clients.

| gRPC status | `x-dfsha-error-code` | HTTP equivalent | When |
|---|---|---|---|
| `UNAUTHENTICATED` | `UNAUTHORIZED` | 401 | Missing, malformed, badly signed or expired block token |
| `PERMISSION_DENIED` | `FORBIDDEN` | 403 | Valid token, but issued for another block or another operation (`op`) |
| `NOT_FOUND` | `BLOCK_NOT_FOUND` | 404 | The block does not exist on this node |
| `INVALID_ARGUMENT` | `BAD_REQUEST` | 400 | Malformed header, missing header, chunk above the limit |
| `INVALID_ARGUMENT` | `CHECKSUM_MISMATCH` | 422 | The received bytes do not match the declared checksum or size |
| `OUT_OF_RANGE` | `RANGE_NOT_SATISFIABLE` | 416 | `offset` / `length` outside the block |
| `DATA_LOSS` | `CHECKSUM_MISMATCH` | 500 | Corruption detected when reading from disk (GCM tag or checksum) |
| `RESOURCE_EXHAUSTED` | — | 507 | The node has no free space |
| `UNAVAILABLE` | — | 503 | The node or a downstream node is unreachable; the client tries another replica or asks for a fresh pipeline |

## 4. NameNode — user and file system API (Client → NameNode)

All require `Authorization` (JWT or API key), except `register` and `login`.

### 4.1 Authentication

| Method | Path | Description |
|---|---|---|
| POST | `/v1/auth/register` | Creates a user |
| POST | `/v1/auth/login` | Credentials step: returns a JWT, or an MFA challenge if 2FA is enabled |
| POST | `/v1/auth/login/2fa` | Code step: exchanges a challenge plus a TOTP (or recovery) code for a JWT |
| POST | `/v1/auth/2fa/enroll` | Starts 2FA enrolment: returns the secret and its `otpauth://` URI, still disabled |
| POST | `/v1/auth/2fa/verify` | Confirms enrolment with the first code; enables 2FA and returns the recovery codes **once** |
| DELETE | `/v1/auth/2fa` | Disables 2FA (requires password **and** a valid code) |
| POST | `/v1/auth/apikeys` | Creates an API key |
| GET | `/v1/auth/apikeys` | Lists the caller's API keys (never the secret) |
| DELETE | `/v1/auth/apikeys/{key_id}` | Revokes an API key |

```jsonc
// POST /v1/auth/register
{ "username": "ana", "password": "********" }          // → 201 { "username": "ana" }

// POST /v1/auth/login   — user without 2FA
{ "username": "ana", "password": "********" }
// → 200
{ "access_token": "<jwt>", "token_type": "bearer", "expires_in": 3600 }

// POST /v1/auth/login   — same endpoint, user WITH 2FA enabled
// → 200   (no token yet; the challenge is single-use and expires in MFA_CHALLENGE_TTL_S)
{ "mfa_required": true, "challenge": "mfa_9f3a...", "expires_in": 300 }

// POST /v1/auth/login/2fa
{ "challenge": "mfa_9f3a...", "code": "492013" }       // 6-digit TOTP, or a recovery code
// → 200
{ "access_token": "<jwt>", "token_type": "bearer", "expires_in": 3600 }
// → 401 UNAUTHORIZED      wrong, expired or already-used code
// → 429 RATE_LIMITED      too many attempts on this challenge

// POST /v1/auth/apikeys
{ "name": "laptop-cli" }
// → 201   (api_key is returned only now)
{ "key_id": "k_81f3", "name": "laptop-cli", "api_key": "dfsha_live_9d2c...", "created_at": "2026-10-16T14:30:00Z" }
```

### 4.1.1 Two-factor authentication

```jsonc
// POST /v1/auth/2fa/enroll          (authenticated, 2FA not yet enabled)
// → 200   the secret is shown only here; 2FA stays DISABLED until /verify succeeds
{ "secret": "E4B6LZGUR2JUDLFF...",
  "otpauth_uri": "otpauth://totp/DFSha:ana?secret=E4B6...&issuer=DFSha",
  "qr_png_base64": "iVBORw0KGgo..." }

// POST /v1/auth/2fa/verify
{ "code": "492013" }
// → 200   recovery codes are returned once and never again
{ "enabled": true,
  "recovery_codes": ["7f2a-91bc", "3d10-4e77", "..."] }   // 10 single-use codes

// DELETE /v1/auth/2fa
{ "password": "********", "code": "492013" }               // → 200 { "enabled": false }
```

**Rules clients must respect**

- `/v1/auth/login` may return **either** shape. A client must branch on `mfa_required` rather than assuming `access_token` is present.
- The challenge is **not** a credential: it carries no authorization and is useless on any endpoint other than `/v1/auth/login/2fa`.
- A code is accepted within a ±1 time-step window (30 s each) to absorb clock skew, and **cannot be reused** inside its own window.
- **API keys bypass 2FA by design.** They are the non-interactive credential for scripts and automation; forcing a second factor on a process that would have to store it next to the first adds nothing. Use an API key, not a password, for unattended jobs.
- 2FA is enforced at login only. Once issued, the JWT is a complete credential and records the factors used in its `amr` claim (`["pwd"]` or `["pwd","otp"]`).

### 4.3 File system

| Method | Path | Description |
|---|---|---|
| GET | `/v1/fs/ls?path=/&limit=1000&cursor=` | Lists a directory (paginated) |
| GET | `/v1/fs/stat?path=/a.txt` | Info about a file or directory (the client's `cd` uses this to validate) |
| POST | `/v1/fs/mkdir` | Creates a directory |
| DELETE | `/v1/fs/rmdir?path=/d&recursive=false` | Removes a directory |
| DELETE | `/v1/fs/rm?path=/a.txt` | Removes a file |
| POST | `/v1/fs/mv` | Renames/moves |
| PUT | `/v1/fs/acl` | Sets permissions of a user or group on a path |
| GET | `/v1/fs/acl?path=/projects` | Lists the ACL of a path |

```jsonc
// GET /v1/fs/ls?path=/projects&limit=2  → 200
{
  "path": "/projects",
  "entries": [
    { "name": "report.pdf", "type": "file", "size": 10485760,
      "modified_at": "2026-10-16T14:30:00Z", "owner": "ana" },
    { "name": "data", "type": "dir", "size": 0,
      "modified_at": "2026-10-15T09:00:00Z", "owner": "ana" }
  ],
  "next_cursor": "eyJhZnRlciI6ImRhdGEifQ"      // null when there are no more entries
}

// GET /v1/fs/stat?path=/projects/report.pdf  → 200
{
  "path": "/projects/report.pdf", "type": "file", "size": 10485760,
  "blocks": 3, "replication": 3, "owner": "ana",
  "created_at": "2026-10-16T14:30:00Z", "modified_at": "2026-10-16T14:30:00Z",
  "checksum": "9f86...0a08"                     // whole-file SHA-256, if provided at commit
}

// POST /v1/fs/mkdir
{ "path": "/projects/data", "parents": false }          // → 201

// POST /v1/fs/mv
{ "src": "/a.txt", "dst": "/projects/a.txt" }           // → 200

// PUT /v1/fs/acl
{ "path": "/projects", "subject": "user:bruno",   "permission": "r" }    // "r" | "rw" | "none"
{ "path": "/projects", "subject": "group:students", "permission": "rw" }
```

**Semantics**
- `rm` removes the file's metadata immediately (it disappears from `ls`); its blocks are deleted afterwards through `delete` commands (Section 7).
- `mv` only changes metadata; blocks are not copied.
- Permissions: the owner always has `rw`. An ACL entry grants `r` or `rw` to a user or group on a path and everything below it. The effective permission is the union of all matching entries.

### 4.4 Locks

Locks coordinate several clients working on the same path. They are enforced by the NameNode, stored in the metadata database, and **expire automatically** (so a crashed client never blocks others forever).

| Method | Path | Description |
|---|---|---|
| POST | `/v1/fs/lock` | Acquires a lock on a path |
| POST | `/v1/fs/lock/{lock_id}/renew` | Extends a lock |
| DELETE | `/v1/fs/lock/{lock_id}` | Releases a lock (`unlock`) |

```jsonc
// POST /v1/fs/lock
{ "path": "/projects/report.pdf", "mode": "shared", "ttl_s": 60 }     // mode: "shared" | "exclusive"
// → 200
{ "lock_id": "lk_55a1", "path": "/projects/report.pdf", "mode": "shared", "expires_at": "2026-10-16T14:31:00Z" }

// POST /v1/fs/lock/lk_55a1/renew
{ "ttl_s": 60 }                                                         // → 200 { "expires_at": "..." }
```

| Held lock | Other users can… |
|---|---|
| `shared` | read (`get`, `stat`), take more `shared` locks. **Cannot** `rm`, `mv`, overwrite (`put overwrite=true`), or take an `exclusive` lock → `423 LOCKED` |
| `exclusive` | nothing: every access to the path from other users returns `423 LOCKED` |

The same user's operations are never blocked by their own locks.

## 5. NameNode — file API (Client → NameNode)

The client **talks to the NameNode only for metadata**; the bytes go directly to the DataNodes.

| Method | Path | Description |
|---|---|---|
| POST | `/v1/files/put` | Starts an upload: the NameNode reserves blocks and returns where to write them |
| POST | `/v1/files/{file_id}/tokens` | Renews tokens (and pipelines) for blocks not yet written |
| POST | `/v1/files/{file_id}/commit` | Confirms the upload; the file becomes visible |
| POST | `/v1/files/{file_id}/abort` | Cancels an upload and releases what was reserved |
| GET | `/v1/files/get?path=/a.txt` | Returns the list of blocks and their replicas for reading |

### 5.1 POST `/v1/files/put`

```jsonc
// Request
{
  "path": "/projects/report.pdf",
  "size": 10485760,
  "overwrite": false
}

// Response 201
{
  "file_id": "7b0c9e0e-5e0a-4a58-9a11-1f0c6a3d2b11",
  "block_size": 4194304,
  "replication": 3,
  "blocks": [
    {
      "index": 0,
      "block_id": "blk_7b0c9e0e_000000",
      "size": 4194304,
      "token": "<block-token-write>",
      "pipeline": [
        { "node_id": "dn1", "addr": "dn1.example.com:9000", "internal_addr": "dn1:9000" },
        { "node_id": "dn2", "addr": "dn2.example.com:9000", "internal_addr": "dn2:9000" },
        { "node_id": "dn3", "addr": "dn3.example.com:9000", "internal_addr": "dn3:9000" }
      ]
    }
    // ... one object per block
  ]
}
```

- `pipeline` is **ordered**. The client opens a gRPC `WriteBlock` stream to `pipeline[0].addr` and puts, in the stream header, the `internal_addr` of the **remaining** nodes (`pipeline[1:]`); the DataNodes forward among themselves (Section 6).
- Blocks of the same file are spread over different DataNodes (Section 7, placement), so a file is partitioned across several nodes **and** each block is replicated.
- The file is **not visible** to `ls`, `stat` or `get` until `commit`.
- While the upload is pending, the path is reserved: another `put` on the same path gets `409 UPLOAD_IN_PROGRESS`.
- With `overwrite=true`, the existing file keeps being served until the new `commit` succeeds (see 5.4).
- An uncommitted upload is cleaned up after `UPLOAD_TTL_S` (its reserved blocks are deleted on the DataNodes through `delete` commands).

### 5.2 POST `/v1/files/{file_id}/commit`

```jsonc
// Request: the client reports what it actually uploaded
{
  "blocks": [
    { "index": 0, "block_id": "blk_7b0c9e0e_000000", "size": 4194304, "checksum": "ab12...ef" }
    // ... one per block
  ],
  "file_checksum": "9f86...0a08"       // optional: SHA-256 of the whole file, for end-to-end verification
}
// Response 200
{ "path": "/projects/report.pdf", "size": 10485760, "blocks": 3, "status": "committed" }
```

The NameNode accepts `commit` only if:
1. all blocks are listed, and the sum of their sizes equals the `size` declared in `put`;
2. **every block has at least `MIN_REPLICAS_COMMIT` replicas confirmed** by the DataNodes (`block-received`, Section 7) — this is the write quorum;
3. the checksums reported by the client match those reported by the DataNodes.

Otherwise: `409 INSUFFICIENT_REPLICAS` or `422 CHECKSUM_MISMATCH`. Calling `commit` again on an already committed file with the same body returns `200` (idempotent). The commit is **one atomic database transaction**: the file becomes visible all at once or not at all.

### 5.3 GET `/v1/files/get?path=...`

```jsonc
// Response 200
{
  "file_id": "7b0c9e0e-5e0a-4a58-9a11-1f0c6a3d2b11",
  "path": "/projects/report.pdf",
  "size": 10485760,
  "block_size": 4194304,
  "checksum": "9f86...0a08",           // whole-file checksum, if the client provided one at commit
  "blocks": [
    {
      "index": 0,
      "block_id": "blk_7b0c9e0e_000000",
      "size": 4194304,
      "checksum": "ab12...ef",
      "token": "<block-token-read>",
      "replicas": [
        { "node_id": "dn2", "addr": "dn2.example.com:9000" },
        { "node_id": "dn1", "addr": "dn1.example.com:9000" }
      ]
    }
  ]
}
```

- `replicas` includes only **live** DataNodes (public `addr` values); the client tries them in order and, if one fails or returns a corrupt block, moves on to the next.
- The client verifies the checksum of every downloaded block (and the whole-file checksum if present) before delivering the data.

### 5.4 Consistency and concurrency model

DFSha files are **write-once-read-many (WORM)** — _decision closed, see Section 11_:

- A committed file is **immutable**. To change it, upload a new version with `overwrite=true`. At `commit`, one database transaction switches the path to the new version and schedules the old blocks for deletion; readers always see either the complete old version or the complete new one, never a mix.
- An in-progress `put` reserves the path (`UPLOAD_IN_PROGRESS` for anyone else), so there are never two concurrent writers.
- Reads never block and are always safe from any replica, because blocks are immutable and checksum-verified.
- Optional explicit locks (Section 4.4) cover cross-client coordination (for example preventing a file from being replaced or removed while a long read session is open).
- Metadata is **strongly consistent** (single leader, ACID transactions). Block replicas are **eventually repaired**: the NameNode restores the target replica count after failures (Section 7).

### 5.5 POST `/v1/files/{file_id}/tokens`

Block tokens expire after `TOKEN_TTL_S`. For long uploads, the client asks for fresh tokens for the blocks it has not written yet:

```jsonc
// Request
{ "indexes": [4, 5, 6] }
// Response 200: same shape as the `blocks` array of `put`, with new tokens (and re-evaluated pipelines
// if a node died in the meantime)
{ "blocks": [ { "index": 4, "block_id": "...", "size": 4194304, "token": "...", "pipeline": [ ... ] } ] }
```

### 5.6 POST `/v1/files/{file_id}/abort`

Cancels a pending upload: the path is released and reserved blocks are scheduled for deletion. `200 {}`. Idempotent.

## 6. DataNode — block service, gRPC (Client → DataNode, DataNode → DataNode)

This is the **block-level read/write API** exposed to clients. It is a gRPC service (`BlockService`) over TLS; the DataNode does **not** expose HTTP endpoints. Every RPC except `Health` requires a block token, sent as call metadata `x-block-token` (Section 2.1).

> **Who defines the messages.** This section fixes the *semantics* and the rules both sides must follow. The exact message definitions will live in a `.proto` file written by the DataNode owner and added to the repository through a Pull Request (team rule at the top of this document). Nothing in that `.proto` may contradict this section; if it needs to, this section is updated in the same PR.

| RPC | Type | Description |
|---|---|---|
| `WriteBlock` | client-streaming | Stores a block and forwards it along the pipeline while receiving it |
| `ReadBlock` | server-streaming | Returns the (decrypted) bytes of a block, or part of it |
| `StatBlock` | unary | Existence, size and checksum of a block (no bytes) |
| `Health` | unary | Node status (no token required) |

### 6.1 Rules for every block transfer

- Blocks are **always streamed in chunks** of at most `BLOCK_CHUNK_SIZE` (default 1 MiB). A DataNode rejects chunks above 2 MiB. gRPC's default message limit is 4 MB, so a block never travels as a single message.
- The first message of a stream is a **header**; every following message carries one **chunk** of plaintext block bytes, in order.
- Call metadata: `x-block-token` (required, except on `Health`) and `x-request-id` (optional).
- Errors use gRPC status codes with the trailing metadata `x-dfsha-error-code` (Section 3.1).

### 6.2 `WriteBlock`

**Header fields:** `block_id`, `size` (bytes), `checksum_sha256` (of the whole plaintext block, as computed by the client) and `pipeline` (ordered list of `internal_addr` of the nodes that **still** have to receive the block; empty on the last node).

The DataNode:
1. Validates the token (interceptor) before reading any chunk.
2. Receives the chunks, computing the SHA-256 on the fly and writing them (encrypted at rest, AES-256-GCM, Section 2.3) to a temporary file.
3. If `pipeline` is not empty, opens its own `WriteBlock` stream to `pipeline[0]`, with header `pipeline[1:]` and the same token, and **forwards each chunk as it arrives**, without waiting for the whole block.
4. When the stream ends, checks size and checksum. On mismatch it deletes the temporary file and fails with `INVALID_ARGUMENT` / `CHECKSUM_MISMATCH`; otherwise it renames the file atomically, so a half-written block is never visible.
5. Notifies the NameNode with `block-received` (REST, Section 7).
6. Replies **once its own part and the rest of the chain are done**, with `block_id`, `size`, `checksum_sha256`, `already_existed` and `failed_downstream` (the nodes of the chain that failed, if any).

Notes:
- Because a node forwards chunks before it has verified the whole checksum, **every node verifies independently** against the checksum in the header. A corrupted stream is rejected by each node and never stored.
- It is **idempotent**: if the block already exists with the same checksum, the node answers OK with `already_existed = true` without rewriting it.
- If a downstream node fails, the DataNode still answers OK for its own copy and lists the failed node in `failed_downstream`. The NameNode completes the missing replica through re-replication, as long as `MIN_REPLICAS_COMMIT` is reached before `commit`.

### 6.3 `ReadBlock`

**Request:** `block_id`, `offset` and `length` (`length = 0` means "until the end of the block").
**Response stream:** a header with the size of the **whole** block, the checksum of the **whole** block and the range actually served, followed by the chunks of the requested range. Partial reads are what makes random access efficient (Section 10).

On every read the DataNode verifies the GCM tag (and the checksum when serving the whole block). If it finds corruption it ends the call with `DATA_LOSS`, notifies the NameNode with `block-corrupt` and deletes the bad copy.

### 6.4 `StatBlock` and `Health`

- `StatBlock(block_id)` returns `block_id`, `size` and `checksum_sha256`, or `NOT_FOUND`. Requires a read token.
- `Health()` returns `node_id`, `status` (`ok` / `degraded`), `free_bytes` and `blocks`. No token.

### 6.5 Development and debugging

Enable **gRPC server reflection** on the DataNodes in development, so the service can be inspected and called with `grpcurl` without the `.proto` at hand. Turn it off outside development.

## 7. NameNode — DataNode API (DataNode → NameNode)

All require `X-Node-Key` and are served **only by the current leader** (Section 9). **The NameNode never initiates connections to DataNodes:** commands travel in the heartbeat and block report responses.

| Method | Path | Frequency |
|---|---|---|
| POST | `/v1/nodes/register` | On startup (and again after a restart) |
| POST | `/v1/nodes/heartbeat` | Every `HEARTBEAT_INTERVAL_S` |
| POST | `/v1/nodes/block-report` | After registering and every `BLOCK_REPORT_INTERVAL_S` |
| POST | `/v1/nodes/block-received` | Every time a new block is stored |
| POST | `/v1/nodes/block-corrupt` | When a damaged block is detected |

```jsonc
// POST /v1/nodes/register
{
  "node_id": "dn1",
  "internal_addr": "dn1:9000",
  "public_addr": "dn1.example.com:9000",
  "capacity_bytes": 107374182400,
  "used_bytes": 0
}
// → 200
{ "heartbeat_interval_s": 5, "block_report_interval_s": 60, "term": 4 }

// POST /v1/nodes/heartbeat
{ "node_id": "dn1", "free_bytes": 107000000000, "used_bytes": 374182400, "active_transfers": 2 }
// → 200
{
  "term": 4,
  "commands": [
    { "cmd": "replicate", "block_id": "blk_7b0c9e0e_000001",
      "targets": [ { "node_id": "dn3", "internal_addr": "dn3:9000" } ],
      "token": "<block-token-write>" },
    { "cmd": "delete", "block_id": "blk_old_000004" }
  ]
}

// POST /v1/nodes/block-report
{ "node_id": "dn1",
  "blocks": [ { "block_id": "blk_7b0c9e0e_000000", "size": 4194304, "checksum": "ab12...ef" } ] }
// → 200 { "term": 4, "commands": [ { "cmd": "delete", "block_id": "blk_orphan_000009" } ] }

// POST /v1/nodes/block-received
{ "node_id": "dn1", "block_id": "blk_7b0c9e0e_000000", "size": 4194304, "checksum": "ab12...ef" }
// → 200 {}

// POST /v1/nodes/block-corrupt
{ "node_id": "dn1", "block_id": "blk_7b0c9e0e_000000" }
// → 200 {}   (the NameNode discards that replica and schedules a new copy)
```

**Commands a DataNode can receive**

| `cmd` | What it must do |
|---|---|
| `replicate` | Read (and decrypt) its local copy of the block and send it with a gRPC `WriteBlock` to the `targets` (using their `internal_addr`), with the provided `token` as `x-block-token` metadata |
| `delete` | Delete the local block (file deletion, orphan block or surplus replica) |

**Fencing:** every response carries the leader's `term`. A DataNode remembers the highest `term` it has seen and **ignores any command whose `term` is lower** (protection against a stale/zombie leader). When it sees a **higher** `term` than before, it sends a full block report right away, because the new leader does not know yet where the replicas are.

**NameNode rules**
- No heartbeat for `DEAD_NODE_TIMEOUT_S` ⇒ the node is marked dead and its replicas stop counting.
- If a block has fewer than `REPLICATION_FACTOR` live replicas ⇒ a `replicate` command is issued (through the heartbeat of a live replica holder) toward a live node with free space that does not already hold that block.
- If a block has more replicas than needed (for example a dead node came back) ⇒ a `delete` command removes the surplus.
- Block reports are compared against the metadata: unknown blocks are orphans (`delete`); blocks the NameNode expected but are missing lower the replica count.
- **Placement of new blocks:** live nodes with the most free space, never repeating a node within the same block, with some randomness so consecutive blocks of the same file spread over different nodes.
- After a leader change, the new leader waits `FAILOVER_GRACE_S` before declaring any DataNode dead, so a failover does not trigger a storm of unnecessary re-replications.

## 9. NameNode high availability (leader lease + shared metadata store)

**Design.** Two (or more) NameNode processes share **one PostgreSQL metadata database** (**hard state**: users, namespace, ACLs, locks, files and their blocks, pending deletes). **Soft state** — which DataNodes are alive, their free space and **where each replica is** — lives in the leader's memory and is rebuilt from heartbeats and block reports; it is never written to the database. Exactly one NameNode is the **leader** at any time; the others are standby.

- **Leader election by lease:** a single row `leader(holder, url, term, lease_expires_at)`. A NameNode becomes leader with one atomic statement that succeeds only if the lease is expired (or already its own), incrementing `term`. The leader renews the lease every `LEASE_S/3`; if it dies, a standby takes over within about `LEASE_S` seconds.
- **Only the leader** serves client and DataNode requests and issues tokens/commands. A standby answers `503 NOT_LEADER` with `leader_url` (read from the `leader` row).
- **No metadata copy is needed** at failover: the standby already sees the same committed data. In-flight uploads (pending in the database) survive a failover; the client simply retries against the new leader.
- **Fencing:** `term` is returned in every DataNode response and carried in commands; DataNodes ignore lower terms (Section 7).
- **Discovery:** clients and DataNodes are configured with a list `NAMENODE_URLS=https://nn1…,https://nn2…`; they try them in order and follow `leader_url` when told.
- **After failover:** the new leader loads the hard state from the database, marks all DataNodes "unknown" for `FAILOVER_GRACE_S`, then resumes normal liveness tracking from fresh heartbeats. DataNodes re-send their block reports as soon as they see the new `term`, which rebuilds the replica locations. Until then `commit` may answer `409 INSUFFICIENT_REPLICAS`; the client simply retries.
- **The metadata store is replicated too:** primary plus a streaming hot standby locally, RDS Multi-AZ in the cloud. Two NameNodes in front of a single database would only move the single point of failure one layer down (`ARCHITECTURE.md` Section 5.2).
- **Degraded mode:** if the leader cannot reach the database to renew its lease it does **not** step down, because no standby could take over either and the outage would become total. It keeps leadership and serves **reads from its cache** while answering `503` to every write, reporting `degraded: true`. The block channel is unaffected, so transfers already in progress continue.

| Method | Path | Description |
|---|---|---|
| GET | `/v1/ha/status` | `{ "node_id": "nn1", "role": "leader" \| "standby", "term": 4, "degraded": false, "leader_url": "https://nn1…", "lease_expires_at": "2026-10-16T14:30:20Z" }` |
| POST | `/v1/ha/stepdown` | Admin-only: the leader releases its lease so the standby can take over (planned handover, and the clean way to demo a failover) |

## 10. Client library API (Python) — proposed shared interface

The CLI is a thin layer over a library. Everything in the CLI is also available programmatically; this is the "basic read/write API for files and blocks from the client" required by the project.

```python
from client import DFShaClient

c = DFShaClient(["https://nn1.example.com", "https://nn2.example.com"])   # NameNode list (HA)
c.login("ana", "********")                       # or: c.use_api_key("dfsha_live_...")

# RF1 - file system management
c.ls("/projects")                                # -> list[Entry], follows pagination
c.stat("/projects/report.pdf")
c.mkdir("/projects/data", parents=False)
c.rmdir("/projects/data", recursive=False)
c.rm("/projects/report.pdf")
c.mv("/a.txt", "/projects/a.txt")
c.set_acl("/projects", subject="group:students", permission="rw")
c.create_group("students"); c.add_members("students", ["bruno", "carla"])

# RF2 - transfer (file level)
c.put_file("./report.pdf", "/projects/report.pdf", overwrite=False)   # split, upload in parallel, commit
c.get_file("/projects/report.pdf", "./copy.pdf")                       # parallel download, verify, join

# RF3 - access: open/close/read/seek/lock (read-only handles, because files are WORM)
with c.open("/projects/report.pdf", "rb", lock="shared") as f:         # lock is optional; released on close()
    f.seek(5_000_000)
    data = f.read(1024)      # fetches only the needed blocks, using offset/length when partial
lk = c.lock("/projects/report.pdf", mode="exclusive", ttl_s=60)        # explicit lock/unlock
c.unlock(lk)

# Block level (what the professor asks for explicitly)
blocks = c.get_block_map("/projects/report.pdf")      # GET /v1/files/get
data   = c.read_block(blocks[0])                      # gRPC ReadBlock, tries replicas in order
alloc  = c.begin_upload("/projects/new.bin", size=8_388_608)           # POST /v1/files/put
c.write_block(alloc.blocks[0], chunk0)                # gRPC WriteBlock, via the pipeline
c.write_block(alloc.blocks[1], chunk1)
c.commit_upload(alloc)                                # POST /v1/files/{id}/commit
```

**Behavior the library must implement**
- Upload and download blocks in parallel (thread pool), with a bounded number of concurrent transfers.
- On a failed read, try the next replica; on a failed write to the first pipeline node, call `/tokens` to get a fresh pipeline and retry that block.
- Block transfers use gRPC: keep one channel per DataNode and reuse it, stream each block in chunks of `BLOCK_CHUNK_SIZE`, and send the block token as `x-block-token` metadata. Treat `UNAVAILABLE`, `DATA_LOSS` and `UNAUTHENTICATED` as "try the next replica or ask for fresh tokens".
- Verify block checksums on read; verify the whole-file checksum when the NameNode returns one.
- On `503 NOT_LEADER` or a connection failure to a NameNode, try the next one (follow `leader_url`) and retry with backoff.
- Hide node locations: the user never specifies a DataNode.
- `cd` is client-side: the library keeps a current directory, resolves relative paths and validates with `stat`.

**CLI mapping:** `dfsha login | apikey create | ls | cd | pwd | mkdir | rmdir | rm | mv | put | get | stat | lock | unlock | share | group`.

## 11. Decisions

### Closed (v0.4)

| # | Decision | Choice | Why |
|---|---|---|---|
| 1 | WORM? | **Yes** | Same model as HDFS in the course material; makes consistency simple and provable |
| 2 | Encryption at rest | **DataNode-side AES-256-GCM** + TLS in transit (client-side as optional extension) | Satisfies the requirement with the least coordination; ACL sharing between users keeps working |
| 3 | RF3 depth | **Read-only `open`/`close`/`read`/`seek` + explicit `lock`/`unlock` + upload reservation**; `write` = `begin_upload`/`write_block`/`commit` | Covers every RF3 verb without breaking WORM |
| 4 | Defaults | `BLOCK_SIZE` 64 MB (demo profile 1 MB), factor 3, quorum 2, timeouts as in Section 1 | Matches HDFS defaults; demo profile makes distribution visible |
| 5 | Metadata store | **PostgreSQL**, shared by the NameNodes | ACID transactions, simple HA story |
| 6 | Token secret distribution | Environment variable / secret on NameNodes and DataNodes only | Simplest; rotation by redeploy |
| 7 | HA mechanism | **Lease row in PostgreSQL + `term` fencing** | Real failover to demonstrate, far less code than a custom consensus protocol |
| 8 | Access control | **Users + groups + ACLs + API keys + TOTP 2FA** | The statement names the whole range, "from user/password, ACL, etc, up to 2FA, API Keys, etc". Both ends are implemented, not just one |
| 9 | Node-to-node identity | **Mutual TLS** with per-node certificates from a cluster CA, in addition to the cluster secret | Answers "security between data and control nodes" with cryptographic per-node identity instead of one shared header value |
| 9 | Protocols | **gRPC** for Client ↔ DataNode and DataNode ↔ DataNode (blocks); **REST** for Client ↔ NameNode and DataNode → NameNode | Streaming and pipelined replication where the data volume is; REST where simplicity, `curl` and `/docs` matter. The block service messages (`.proto`) are owned by the DataNode owner |

| B | PostgreSQL replica for HA of the database | Stretch goal / state as a limitation |

## 12. How to use this contract

- **Client:** implements sections 4, 5, the client side of 6, and the library in 10. To develop without waiting for the other components, use mocks built from the example responses in this document.
- **DataNode:** implements Section 6 (gRPC server) and Section 7 as a REST client of the NameNode; it serves no HTTP. It can be tested on its own with `grpcurl` (server reflection on in development) and `curl` against a mock NameNode.
- **NameNode:** implements sections 2, 3, 4, 5, 7 (as the server), 8 and 9. Publishes the OpenAPI generated by FastAPI at `/docs`; it must match this document.
- **Integration test:** `docker-compose up` with PostgreSQL + 2 NameNodes + 3 DataNodes and the scenarios in `ARCHITECTURE.md` Section 12 (including killing a DataNode and killing the leader NameNode).
